## 背景

`bun src/main/index.ts` などでプロセスが **終了コード 1** になっても、標準エラーに何も出ないことがあり、原因の切り分けが難しい。

例: 受け入れや手元の起動で `echo $?` が `1` になるが、画面上・ログ上は無言で終了している。

## 現状（GH-1 実装）

| 経路 | stderr |
|------|--------|
| `CURSOR_API_KEY` 未設定・空・空白のみ（AC-004 相当） | **なし**（`loadStartup` → `kind: 'exit', code: 1`） |
| `issue-runner.json` が JSON として読めない | 「設定ファイルを読めません: issue-runner.json」 |
| 設定フローで `savedConfig` が無いまま終了（`runSettingsFlow`） | **なし**（現状のコードパスでは稀だが、同様に無言） |

`src/main/index.ts` は `startup.stderr` が定義されているときだけ `process.stderr.write` するため、**stderr 未設定の exit 1 は完全に無言**になる。

仕様タスクでは API キーについて「**キーの値**は stderr に出さない」とあるが、**理由の文言そのものを出さない**要件ではない。一方 AC-004 は終了コード 1 と TUI 非表示のみを要求しており、無言終了を明示的に求めているわけでもない。

## 望ましい改善

- 終了コードが 0 以外のとき、利用者が次に何をすべきか分かる **短い日本語メッセージを stderr に 1 行以上**出す（API キー値・トークンは引き続き出さない）。
- 少なくとも次をカバーする:
  - `CURSOR_API_KEY` が無い／空／空白のみ → 設定方法のヒント（将来 #7 の SDK ログイン経路があれば併記）
  - 設定ファイル読み取りエラー（既存文言の維持）
  - その他 `process.exit(1)` 相当の経路があれば同様に理由を揃える
- 自動テストで「exit 1 ⇒ stderr に期待文言（または非空）」を観測する（`src/config/index.test.ts` の「no stderr」期待は仕様変更に合わせて更新）。
